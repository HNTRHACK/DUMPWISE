# Database Schema — Phase 1

PostgreSQL 17, managed with Prisma 7.10.1. Source of truth: `apps/api/prisma/schema.prisma`.
Migration: `apps/api/prisma/migrations/20261022193934_init` (Prisma-generated SQL plus
hand-written CHECK constraints at the end).

All primary keys are PostgreSQL `uuid` values generated by `gen_random_uuid()`. Timestamps
are `timestamptz`. Table and column names are snake_case.

## Entity relationships

```
organizations 1─* memberships *─1 users
organizations 1─* import_batches 1─* sales_transactions *─1 products
                                   │                     *─1 distributors
                                   │                     *─1 customers
                                   └─* reconciliation_results
organizations 1─* audit_events *─0..1 users
```

### Tenant isolation in the database

Every business table has `organization_id`. Children reference parents through
**composite foreign keys** `(organization_id, <parent>_id) → parent(organization_id, id)`.
For that to work, each parent has a `UNIQUE (organization_id, id)`. As a result, a sales
transaction of organization A cannot reference a product, distributor, customer or batch of
organization B: PostgreSQL rejects the insert. A test proves this.

## Tables

| Table | Purpose | Keys and constraints |
|---|---|---|
| `organizations` | Tenants. `data_classification` ∈ {SYNTHETIC, PRODUCTION} | `slug` unique |
| `users` | People (email stored lower-case) | `email` unique |
| `memberships` | User ↔ organization with `role` ∈ {OWNER, ANALYST, VIEWER} | unique `(organization_id, user_id)`; index `user_id` |
| `import_batches` | One per import attempt: file SHA-256, size, counts, capped issue list (JSON), `status`, `reconciliation_status`, publish info | unique `(organization_id, id)`; index `(organization_id, status)`, `(organization_id, file_sha256)`; CHECK sha is 64 hex chars |
| `products` | SAP materials | unique `(organization_id, sku)`, `(organization_id, id)` |
| `distributors` | SAP sold-to parties | unique `(organization_id, code)`, `(organization_id, id)` |
| `customers` | SAP ship-to parties (end customer reference) | unique `(organization_id, code)`, `(organization_id, id)` |
| `sales_transactions` | One row per SAP billing item | see below |
| `reconciliation_results` | One row per check (metric × month × currency/unit) | index `(organization_id, import_batch_id)`; CHECK month `YYYY-MM` |
| `audit_events` | Append-only log: action, entity, actor, JSON metadata | index `(organization_id, created_at)` |

### `sales_transactions`

| Column | Type | Notes |
|---|---|---|
| billing_document | varchar(20) | SAP VBELN, string with leading zeros |
| billing_item | varchar(10) | SAP POSNR, e.g. `000010` |
| billing_type | enum F2/G2/RE/S1 | |
| billing_date | date | No time zone; the month is unambiguous |
| cancelled_billing_document | varchar(20) null | Required for S1 (CHECK) |
| distributor_id / product_id / customer_id | uuid | Composite FKs with organization_id |
| quantity | numeric(18,3) | **Signed** (see sign rules) |
| sales_unit | varchar(10) | |
| net_amount | numeric(18,2) | **Signed**, document currency |
| currency | char(3) | CHECK `^[A-Z]{3}$` |
| content_hash | char(64) | SHA-256 of business content |
| source_row_number | int | Line in the source file |

- Unique `(organization_id, billing_document, billing_item)`: the SAP business key and the deduplication key.
- Indexes on `(organization_id, billing_date)`, `(organization_id, import_batch_id)`, and `(organization_id, distributor_id | product_id | customer_id)` for distributor-, SKU- and customer-wise analysis.
- CHECK `sales_transactions_sign_check`: F2 has non-negative amount and quantity; G2 has non-positive amount and zero quantity; RE and S1 have non-positive amount and quantity.

All foreign keys use `ON DELETE RESTRICT`: nothing cascades away silently.

## Database roles

| Role | Used by | Privileges |
|---|---|---|
| `dumpwise` (container superuser) | Prisma migrations, `scripts/setup-db-roles.ts`, test DB setup | Everything (local development only) |
| `dumpwise_app` | The API, CLI and tests (`DATABASE_URL`) | `SELECT, INSERT, UPDATE` on business tables; **no** DELETE, TRUNCATE or DDL; `audit_events`: INSERT and SELECT only; no access to `_prisma_migrations` |

Run `npm run db:roles` after every new migration. `npm run db:migrate` does this
automatically. The script is idempotent.
